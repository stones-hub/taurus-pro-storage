## 目标与边界

Redis 队列目标为至少一次投递：在明确的 Redis 数据持久性前提下，入队成功的任务不因消费者进程崩溃而静默丢失；未确认任务可恢复，允许重复投递。业务副作用幂等由接入方负责，组件不依赖业务表、不接管业务事务、不承诺恰好一次。

Channel 引擎保持易失内存队列，不承诺进程崩溃恢复。Redis 的持久化、复制、淘汰和故障切换边界必须在运行要求中明确；单机或普通异步复制不能被描述为零丢失保证。

不新增管理页面、不引入额外消息平台，不重写全部数据库 API。

## 已确认的关键代码事实（均指基线 33292a8，当前候选已针对性修改，未逐项复现）

1. Reader 先弹出 Source 再写 Processing，Worker 先弹出 Processing 再执行业务，存在消息已删除但尚未完成的窗口。
2. `Manager.recoverLastData()` 当前为空实现。
3. 引擎多处 recover 仅打印，可能返回零值成功；Worker 外层 recover 会结束该 Worker。
4. Stop 先取消处理上下文，等待超时不返回失败；Start 未重建关闭状态。
5. 延迟队列查询、删除分离；失败队列会自动再次调用同一 Processor。
6. 部分落盘失败只记录日志；time.After 包装不取消底层写入，可能出现迟到成功。
7. 数据库连接 map 无同步且直接暴露；连接尝试次数为零可能触发空指针。

## 建议的最小目标架构

### Redis 消费：建议 Streams 消费者组

建议采用 Streams 原生 pending/ack 能力，避免在 List 上自行建设同等规模的在途登记与恢复机制。本节记录已接受的设计方向；最终实际实现和验证范围以queue-reliability.md及production-reliability-verification.md为准。

- 新任务进入一个 ready Stream，Worker 通过消费者组领取；不再通过 Reader 二次搬运 Redis 消息。
- 消费凭证至少包含消息 ID 和本次领取身份/代际；成功才确认。
- 到期 pending 可重新领取。领取续期、恢复、确认和失败转移必须校验当前领取权；仅有 XACK 或 consumer 名称检查不足以自动证明隔离正确。
- 旧执行者不能确认或转移已由新领取者接手的任务。不能强制终止不配合 context 的 Processor；可能重叠执行，需在接入契约中明确幂等要求。
- 重试使用持久延迟集合；转入延迟集合并确认原消息必须原子完成或具备可证明的恢复协议。
- 到期任务搬回 ready 必须原子完成；失败终态写入持久失败集合/Stream 并确认原消息，同样不能留丢失窗口。
- 重试耗尽和不可重试错误进入失败留存，不自动再调业务处理器。提供最小可查询、显式重放能力，重放保留任务关联且不能静默覆盖。
- 不盲目裁剪 ready Stream；保留策略必须保护未确认消息，也不能无限增长。清理条件与并发领取一起验收。
- 暂不支持该可靠路径在 Redis Cluster 上运行；如确需支持，需先定义所有参与原子操作的 key 使用同一 hash slot 并验收。不得把单机 Lua 成功当作 Cluster 兼容证明。

实际实现使用租约ZSet、Token及Lua结合Streams消费者组，不使用XAUTOCLAIM。代码6.2准入门槛不等于兼容验证，仅Redis8.10.2实际验收通过。目标部署拓扑未知，生产兼容性未满足。

### 公共接口与兼容

- 尽量保留 `Processor.Process(ctx, data)`、`NewManager` 和 `AddData` 的基本调用形态。
- 现有导出的 Engine 是破坏性 Pop 接口，不能悄悄让它宣称可靠消费。优先新增单独的可靠投递接口，保留旧接口用于兼容/内存路径；新可靠路径不依赖破坏性 Pop。
- 可靠接口应覆盖领取、确认、续期、重试/终态转移与恢复；准确 Go 签名在任务书中锁定后才编码。
- AddData 网络超时必须描述为结果可能不确定；建议提供可由调用方指定稳定任务 ID 的入队入口，避免每次重试自动生成不同 ID。去重范围、保留时长须明确，不能承诺无限去重。
- ReaderCount、Processing 等旧配置在新路径中的处理必须明确：废弃说明或验证时报错，不得默默忽略并误导用户。
- false 配置不得被默认合并覆盖；零次重试、无效队列名、冲突名称应有明确约定和验证。
- Manager 建议先采用单次生命周期：Stop 后再次 Start 返回明确错误，避免增加不必要的重建逻辑。属于行为兼容变化，需发布说明。
- Stop 停止领取后允许在途任务在期限内结束，必要的确认/转移使用独立限时上下文；未完成任务保留可恢复状态。超时返回错误，不假装所有 goroutine 已退出。

### 旧数据与发布

> 状态：以下是方案提案。当前实现没有迁移工具，现有入口也无法保留旧延迟/重试/失败状态，迁移受阻且未验收，见 `docs/queue-reliability.md`。

List 与 Stream 不能共用同一个 Redis key，也不能让新旧消费者并发处理同一队列。

建议作为明确的破坏性版本发布（具体版本号按现有标签策略确认）：

1. 在隔离测试环境验证旧版本数据格式和迁移方案。
2. 升级时暂停生产者及旧消费者，核对 Source、Processing、Retry、Failed 中的所有数据并备份。
3. 将仍存留的数据迁移至新命名空间；迁移需要持久检查点、可重入和数量核对，不能先删除旧数据再导入。旧重试/失败项分别保留其语义。
4. 验证迁移后再启用新消费者及生产者。旧版本已经弹出且未留存的数据无法由迁移凭空恢复。
5. 新版运行后的消息不能直接交给旧版消费；回滚需停机及反向数据处理方案，不能只回退二进制。

迁移工具和生产操作另行授权；本阶段只设计，不操作 Redis。

## 放行标准

以下均需实际运行证据，不以静态推导或单元测试绿灯替代：

- 入队结果和超时不确定性有明确可观测行为；稳定 ID 重试符合去重契约。
- 领取后 kill、处理成功但确认前 kill：任务可恢复，允许重投。
- 双实例恢复与长任务续期：旧领取者不能错误确认新领取；崩溃消费者不会永久占用任务。
- panic 不导致消息消失或 Worker 静默退出。
- 延迟转移、失败转移的每个中断点均无静默丢失，重试预算正确。
- 失败消息持久留存、可查询、显式重放；重放失败不删除原记录。
- Redis 断连、响应丢失、重启与持久化恢复均在既定边界内表现正确。
- Stop 期间不再领取新任务；超时诚实返回错误，未结束任务可恢复；二次 Start/Stop 行为明确。
- Stream 清理不删除未完成任务，持续负载下存储增长有边界。
- 旧 List/延迟集合迁移可重入、可核对，并有失败处置演练。
- DB 无效参数、并发连接管理、事务回滚、更新零值及排序验证有自动化覆盖。
- 每个已接收任务均能核对到成功、待处理、执行中、待重试或失败留存；重复投递与重复业务效果分开计量。

目标 QPS、任务时长、积压规模、Redis 拓扑未确定前，不给出容量或故障切换零丢失承诺。
